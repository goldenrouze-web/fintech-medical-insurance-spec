## 1. Введение

### 1.1. Назначение

SRS/BRD для учебного финтех-продукта «MedInsure» — веб-платформы оформления и обслуживания полисов ДМС. Аудитория: Product Owner, разработчики, QA.

### 1.2. Scope MVP

Система покрывает: онлайн-конструктор и покупку полиса (B2C), оплату премии (карта, СБП), управление договором, подачу и ручную обработку claims, личные кабинеты клиента и сотрудника.

**Out of Scope MVP:** мобильные приложения, B2B-модуль, агентский модуль, ЕСИА, SSO, рассрочка, ЭДО, прямой биллинг с клиниками, AI-валидация документов, автоодобрение claims, анти-фрод, телемедицина, 2FA, аудит-лог, страхование жизни / КАСКО / ОСАГО.

### 1.3. Ссылки

IEEE Std 830-1998, ФЗ № 4015-1, ФЗ № 152-ФЗ, ФЗ № 54-ФЗ.

## 2. Бизнес-требования

### 2.1. Проблема

Большинство полисов ДМС оформляется офлайн. Урегулирование убытков занимает 10–30 дней из-за ручного сбора справок. Нет цифрового self-service канала для покупки полиса и подачи claims.

### 2.2. Бизнес-цели

| ID | Цель | Метрика (12 мес) |
|---|---|---|
| BG-01 | Снизить стоимость привлечения клиента | CAC ≤ 40% от агентского канала |
| BG-02 | Сократить срок урегулирования | Claim → выплата ≤ 5 рабочих дней |
| BG-03 | Удовлетворённость клиентов | NPS ≥ 45 |
| BG-04 | Самообслуживание | ≥ 80% полисов без оператора |

### 2.3. Заинтересованные стороны

| Роль | Интерес |
|---|---|
| Product Owner | Запуск MVP в срок |
| Клиент B2C | Простая покупка, прозрачные выплаты |
| Claims-специалист | Удобная обработка заявлений |
| Администратор | Управление пользователями и настройками |

### 2.4. Бизнес-процессы

**Покупка полиса:** конструктор → анкета здоровья → фото паспорта → расчёт премии → оплата → электронный полис в ЛК и на email.

**Страховой случай:** подача claim через ЛК → рассмотрение специалистом → решение (одобрить / отклонить) → выплата.

## 3. Общее описание продукта

### 3.1. Архитектура

Модульный монолит — простота развёртывания и отладки для учебного проекта.

- **Frontend:** React + TypeScript (адаптивная вёрстка)
- **Backend:** Java 21 / Spring Boot (модули: policy, billing, claims, user, notification)
- **БД:** PostgreSQL
- **Файлы:** MinIO в Docker
- **Мониторинг:** Prometheus + Grafana, логи через stdout

### 3.2. Роли пользователей

| Роль | Задачи |
|---|---|
| Клиент B2C | Купить полис, подать claim |
| Claims-специалист | Рассматривать заявления, выплаты |
| Андеррайтер | Утверждать/отклонять выпуск полиса |
| Администратор | Управлять пользователями, ролями, справочниками |

### 3.3. Операционная среда

Docker Compose (PostgreSQL, MinIO, backend, frontend). Платежи и SMS — sandbox/моки. Браузеры: Chrome, Safari, Firefox, Edge (две последние major-версии).

## 5. Сценарии использования

### UC-01. Покупка полиса

**Актор:** Клиент. **Предусловие:** зарегистрирован, паспорт верифицирован. **Результат:** активный полис.

1. Выбирает программу и опции.
2. Заполняет декларацию.
3. Система рассчитывает премию.
4. Принимает правила, оплачивает через шлюз.
5. Получает PDF на email, полис в ЛК со статусом `Active`.

**Альтернативный поток:** платёж отклонён → полис `Pending Payment` (24 ч), предлагается повторить.

### UC-02. Подача claim

**Актор:** Застрахованный. **Предусловие:** активный полис.

1. Указывает тип события, дату, клинику, сумму.
2. Прикрепляет документы.
3. Claim создаётся со статусом `Submitted`, email-подтверждение.

### UC-03. Рассмотрение claim

**Актор:** Claims-специалист.

1. Открывает очередь `Submitted`.
2. Просматривает документы и данные полиса.
3. Решение: одобрить (с суммой) / отклонить / запросить доп. документы.
4. Система обновляет статус, уведомляет клиента.

## 9. Ограничения и допущения

**Ограничения:** срок MVP — 3 месяца, команда 1–3 человека, стек: Java 21 + Spring Boot, React 18, PostgreSQL, Docker Compose.

## 12. Приложения

### Приложение A. Статусная модель полиса

```
Draft → Pending Payment → Active → Expired
              │                      │
              │ (timeout 24ч)        │ (клиент)
              ▼                      ▼
          Cancelled              Cancelled
```

| Статус | Описание |
|---|---|
| `Draft` | Создан, не оплачен |
| `Pending Payment` | Ожидает оплаты (24 ч, затем → Cancelled) |
| `Active` | Действующий |
| `Expired` | Срок истёк |
| `Cancelled` | Расторгнут или отменён по таймауту |

### Приложение B. Статусная модель claim

```
Submitted → In Review → Approved → Paid
                │
                ├─→ Pending Docs → In Review
                │
                └─→ Rejected
```

| Статус | Описание |
|---|---|
| `Submitted` | Подан клиентом |
| `In Review` | На рассмотрении |
| `Pending Docs` | Запрошены доп. документы |
| `Approved` | Одобрен |
| `Paid` | Выплачен |
| `Rejected` | Отклонён |
