## 1. Введение

### 1.1. Назначение документа

Документ содержит бизнес-требования (BRD) и спецификацию требований к ПО (SRS) для учебного финтех-продукта «MedInsure» — веб-платформы оформления и обслуживания полисов добровольного медицинского страхования (ДМС).

Целевая аудитория документа: Product Owner, аналитики, разработчики, QA-инженеры.

### 1.2. Область применения (Scope)

Система «MedInsure» в рамках MVP покрывает:

- онлайн-конструктор и покупка полиса ДМС физическими лицами (B2C);
- оплата премии (банковская карта, СБП);
- управление договором (просмотр, расторжение);
- подача и ручная обработка заявлений на страховые выплаты (claims);
- личный кабинет клиента и сотрудника страховщика.

**Вне области (Out of Scope) MVP:**

- страхование жизни, КАСКО, ОСАГО и иные виды, кроме ДМС;
- перестрахование и актуарные расчёты высокой сложности;
- собственная ЭМК (электронная медицинская карта);
- мобильные приложения (iOS/Android) — только адаптивный веб;
- корпоративный B2B-модуль (массовое оформление для юрлиц);
- агентский модуль (реферальные ссылки, комиссии);
- интеграция с ЕСИА / Госуслуги;
- SSO через SAML / OIDC;
- рассрочка платежа;
- интеграция с ЭДО (Диадок / СБИС);
- интеграция с клиниками-партнёрами (прямой биллинг);
- AI-валидация документов и автоодобрение claims;
- анти-фрод скоринг;
- телемедицина.

## 2. Бизнес-требования (BRD)

### 2.1. Бизнес-контекст и проблема

Рынок ДМС характеризуется низким уровнем цифровизации: большинство полисов оформляется офлайн через агентов или HR-отделы. Клиентский путь при страховом случае включает ручной сбор бумажных справок и длительные сроки возмещения (10–30 дней).

**Ключевая проблема:** нет цифрового self-service канала, объединяющего покупку полиса, оплату и подачу заявлений на выплату в одном интерфейсе.

### 2.2. Бизнес-цели

| ID | Цель | Целевая метрика (12 мес) |
|---|---|---|
| BG-01 | Снизить стоимость привлечения клиента через цифровой канал | CAC ≤ 40% от агентского канала |
| BG-02 | Сократить срок урегулирования убытка | Среднее время claim → выплата ≤ 5 рабочих дней |
| BG-03 | Обеспечить удовлетворённость клиентов | NPS ≥ 45 |
| BG-04 | Доля полисов, оформленных без оператора | ≥ 80% |

### 2.3. Заинтересованные стороны

| Роль | Интерес | Влияние |
|---|---|---|
| Product Owner | Запуск MVP в срок и бюджет | Высокое |
| Страхователь B2C | Простая покупка, прозрачные выплаты | Высокое |
| Андеррайтер / Claims-специалист | Удобная обработка заявлений | Высокое |
| Администратор системы | Управление настройками и пользователями | Среднее |

### 2.4. Бизнес-процессы верхнего уровня

**Процесс 1. Покупка полиса (B2C)**

1. Клиент выбирает программу в конструкторе.
2. Заполняет анкету здоровья.
3. Загружает фото паспорта для верификации.
4. Получает расчёт премии.
5. Оплачивает через карту или СБП.
6. Получает электронный полис в ЛК и на email.

**Процесс 2. Страховой случай (Claim)**

1. Застрахованный подаёт claim через ЛК: тип события, чеки, медзаключения.
2. Claims-специалист рассматривает заявление, при необходимости запрашивает доп. документы.
3. Принимает решение (одобрить / отклонить).
4. При одобрении — выплата на карту или по СБП.

## 3. Общее описание продукта

### 3.1. Архитектура

«MedInsure» — веб-приложение с модульной монолитной архитектурой. Для учебного проекта это оптимальный выбор: простота развёртывания, отладки и сопровождения без накладных расходов распределённой системы.

Компоненты:

- **Frontend:** SPA на React + TypeScript (адаптивная вёрстка);
- **Backend:** модульный монолит на Java 21 (Spring Boot), внутренние модули: policy, billing, claims, user, notification;
- **БД:** PostgreSQL (транзакции и хранение данных);
- **Файловое хранилище:** MinIO (S3-совместимое, поднимается в Docker);
- **Мониторинг:** Prometheus + Grafana (метрики и алерты), логи через stdout → Loki или файл.

### 3.2. Функции продукта

- **F1. Конструктор полисов** — выбор программ, опций, расчёт премии.
- **F2. Биллинг** — оплата премии, возвраты.
- **F3. Управление полисами** — жизненный цикл договора.
- **F4. Обработка claims** — подача, рассмотрение, выплата.
- **F5. Личные кабинеты** — клиент и сотрудник страховщика.
- **F6. Уведомления** — email и SMS.
- **F7. Администрирование** — роли, права, аудит.

### 3.3. Роли пользователей

| Роль | Ключевые задачи |
|---|---|
| Страхователь (клиент B2C) | Купить/продлить полис, подать claim, просмотреть историю |
| Claims-специалист | Рассматривать заявления, принимать решения по выплатам |
| Андеррайтер | Просматривать анкеты здоровья, утверждать/отклонять выпуск полиса |
| Администратор | Управлять пользователями, ролями, справочниками |

### 3.4. Операционная среда

- **Клиент (web):** Chrome, Safari, Firefox, Edge — две последние major-версии.
- **Серверная часть:** Docker Compose (PostgreSQL, MinIO, backend, frontend).
- **Стек:** backend — Java 21 / Spring Boot; frontend — TypeScript + React 18.
- **Учебное окружение:** данные клиник и реальные платежи заменяются sandbox/моками.

## 5. Сценарии использования

### 5.1. UC-01. Покупка полиса ДМС

**Актор:** Клиент B2C
**Предусловие:** Пользователь зарегистрирован и прошёл верификацию паспорта.
**Постусловие:** Выпущен активный полис, произведена оплата.

**Основной сценарий:**

1. Пользователь открывает «Купить полис».
2. Выбирает программу и опции в конструкторе.
3. Заполняет медицинскую декларацию.
4. Система рассчитывает премию и показывает сводку.
5. Пользователь принимает правила и согласие на обработку ПДн.
6. Выбирает способ оплаты, переходит на форму шлюза, оплачивает.
7. Система получает подтверждение, выпускает полис, отправляет PDF на email.
8. Полис отображается в ЛК со статусом `Active`.

**Альтернативные потоки:**

- **4a.** Декларация выявила высокий риск → система показывает надбавку или отказ с пояснением.
- **6a.** Платёж отклонён → предлагается повторить или выбрать другой метод; полис в статусе `Pending Payment` (24 ч).

### 5.2. UC-02. Подача claim

**Актор:** Застрахованный
**Предусловие:** Есть активный полис.

1. Пользователь открывает «Подать заявление».
2. Выбирает полис, тип события, указывает дату, клинику, сумму.
3. Прикрепляет документы (чеки, заключения).
4. Подтверждает согласие на обработку медданных.
5. Система создаёт claim со статусом `Submitted`.
6. Пользователь видит claim в ЛК и получает email-подтверждение.

### 5.3. UC-03. Рассмотрение claim

**Актор:** Claims-специалист

1. Специалист открывает очередь claims со статусом `Submitted`.
2. Выбирает claim, просматривает документы, данные полиса.
3. Принимает решение: одобрить / отклонить / запросить доп. документы.
4. При одобрении — указывает сумму выплаты (с учётом франшизы/лимитов).
5. Система обновляет статус, инициирует выплату, уведомляет клиента.

## 7. Внешние интерфейсы и интеграции

- Web SPA (React + TypeScript, адаптивная вёрстка);

### 7.3. Внешние системы

| Система | Назначение | Примечание для MVP |

| Email-провайдер (SMTP) | Уведомления, чеки, PDF полиса | Локальный Mailhog или реальный SMTP |
| MinIO | Хранение документов (сканы, PDF) | Docker-контейнер |

## 9. Ограничения, допущения и зависимости

### 9.1. Ограничения

- Сроки MVP — 3 месяца.
- Команда — 1–3 разработчика (учебный проект).
- Стек зафиксирован: Java 21 + Spring Boot, React 18, PostgreSQL, Docker Compose.

### 9.2. Допущения

- Платёжный шлюз работает в sandbox-режиме (реальные деньги не списываются).
- Верификация паспорта выполняется вручную сотрудником (без OCR/liveness).
- Данные клиник и тарифы — тестовые fixtures.

### 9.3. Зависимости

- Доступность sandbox-API платёжного шлюза.
- Утверждение тарифной сетки (тестовых коэффициентов).

## 12. Приложения

### Приложение A. Статусная модель полиса

Единственное место определения статусов полиса.

```
Draft → Pending Payment → Active → Expired
                │                    │
                │ (timeout 24ч)      │ (клиент)
                ▼                    ▼
            Cancelled            Cancelled
```

| Статус | Описание |
|---|---|
| `Draft` | Полис создан, параметры выбраны, не оплачен |
| `Pending Payment` | Ожидает оплаты (TTL 24 часа, затем → Cancelled) |
| `Active` | Действующий полис |
| `Expired` | Срок действия истёк |
| `Cancelled` | Расторгнут клиентом или отменён по таймауту |

### Приложение B. Статусная модель claim

Единственное место определения статусов claim.

```
Submitted → In Review → Approved → Paid
                │            
                ├─→ Pending Docs → In Review
                │
                └─→ Rejected
```

| Статус | Описание |
|---|---|
| `Submitted` | Подан клиентом |
| `In Review` | На рассмотрении у специалиста |
| `Pending Docs` | Запрошены дополнительные документы |
| `Approved` | Одобрен, ожидает выплаты |
| `Paid` | Выплата произведена |
| `Rejected` | Отклонён (с указанием причины) |
